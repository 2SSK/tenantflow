# ADR-0004: Saga orchestration with compensation

- Status: accepted
- Date: 2026
- Deciders: project owner

## Context

Multi-step tenant operations (provision, upgrade, delete, …) can fail mid-way
after side effects happened. We needed a principled answer: either roll back
everything, or roll back *enough* and leave a recoverable state.

## Decision

Each lifecycle workflow is a **saga**: a sequence of activities where each
step that mutates durable state registers a compensation activity; on failure
the workflow runs compensations, then `CompensationBookkeeping` records the
outcome on a durable timeline (`internal/activities/compensation.go`).
Corrections themselves are idempotent and retried (see
`docs/idempotency.md`). Rejected alternatives:

- **Choreography (events between services)**: harder to trace, harder to make
  retry-safe, and the single-worker control plane has no independent services
  to choreograph anyway.
- **Distributed transactions (2PC)**: Temporal + Postgres + Keycloak do not
  share a transaction manager, and 2PC across heterogeneous resources is
  operationally fragile.

## Consequences

Positive:

- Every saga's failure behavior is *mapped*, not assumed:
  `docs/failure-matrix.md` lists each activity, what compensates it, and what
  the retry-window proof is.
- The recorder (`internal/worker`) persists failed runs as audit rows so
  operators see exactly where a saga died.

Negative:

- Compensation is per-saga code, not a framework — acceptable because each
  saga's compensation set is small and explicit.
- Some failures cannot be fully compensated (e.g. keycloak user deleted but
  DB not dropped) — the matrix states the residual state and the operation
  that fixes it (manual `DestroyTenant` re-run / retry endpoints).
